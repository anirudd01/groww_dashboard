# Zerodha Kite Connect — how the heatmap uses it

Kite is the fourth market-data provider for the sector heatmap
([`market/providers/kite.py`](../../market/providers/kite.py)). It is
**read-only**: nothing in the Kite code path calls an order, GTT or alert
endpoint, and [`tests/test_kite.py`](../../tests/test_kite.py) fails if one
appears.

Upstream reference: <https://kite.trade/docs/connect/v3/>. Every page there is
also available as Markdown by appending `.md`. Zerodha's agent-setup notes are
in [`../KITE_PROMPT.md`](../KITE_PROMPT.md).

## Credentials and the daily login

| Variable | Needed by | Notes |
|---|---|---|
| `KITE_API_KEY` (or `KITE_APIKEY`) | everything | Public app key from developers.kite.trade |
| `KITE_API_SECRET` | `scripts/kite_login.py` only | Used once to compute the checksum; never saved |
| `KITE_ACCESS_TOKEN` | optional | Overrides the saved session, e.g. a token minted elsewhere |

Kite tokens come from a browser login and **expire at 06:00 IST** every day.
This is a regulatory rule, and nothing can refresh them. Each trading morning:

```bash
python scripts/kite_login.py            # 1. opens Zerodha's login page
                                        # 2. you log in there (password/TOTP never touch this code)
                                        # 3. paste the address the browser was redirected to
python scripts/kite_login.py --status   # is the saved token still accepted?
python scripts/kite_login.py --logout   # revoke it on Kite and delete it locally
```

The redirect page may fail to load, and that doesn't matter. Only its address
is needed: it carries `request_token=...`, which is **single-use and lasts a few
minutes**. The script POSTs it with `checksum = sha256(api_key + request_token +
api_secret)` to `/session/token`. It then saves the resulting access token to
the shared database (`data/market.db`, git-ignored) with its expiry, which is the first 06:00
IST after login. The provider reads that file each time a board connects,
so a new login is picked up without restarting the dashboard. A session that
belongs to another key, or has passed 06:00, is ignored and logged.

Until someone logs in, `is_configured()` is false. Kite then shows as "no
credentials" and *Auto* moves on to the next broker.

## Plans

Quotes, historical candles and the websocket require the paid **Kite Connect**
plan. The free **Personal** plan covers orders and portfolio only. `connect()`
probes one LTP quote, so a key without the data plan fails at connect with a
message that names the plan. The alternative would be a board that quietly
shows nothing.

## Two ids per instrument

| API | Identifies an instrument by | Example |
|---|---|---|
| REST quotes | `exchange:tradingsymbol`, repeated `i=` params | `i=NSE:RELIANCE&i=NSE:NIFTY BANK` |
| Websocket, historical candles | numeric `instrument_token` | `738561`, `260105` |

Kite's `instrument_token` is **not** the NSE token used by Dhan and INDmoney.
RELIANCE is `738561` on Kite; its `exchange_token` column is the NSE `2885`. So
the `kite_instruments` set in `data/market.db` stores the
instrument token as `security_id` (becoming `InstrumentRef.provider_id`) and
the `tradingsymbol` alongside it. The file is generated by
[`scripts/kite.py --master`](../../scripts/kite.py)
from `https://api.kite.trade/instruments/NSE`, which needs no login.

Index names mostly match the dashboard's symbols. The script's `INDEX_NAMES`
lists the five that differ:

| Dashboard | Kite tradingsymbol | Not to be confused with |
|---|---|---|
| `NIFTY` | `NIFTY 50` | |
| `BANKNIFTY` | `NIFTY BANK` | |
| `FINNIFTY` | `NIFTY FIN SERVICE` | `NIFTY FINSRV25 50` (capped), `NIFTY FINSEREXBNK` (ex-bank) |
| `NIFTYIT` | `NIFTY IT` | |
| `NIFTYNXT50` | `NIFTY NEXT 50` | |

## Endpoints used

| Purpose | Endpoint | Limit |
|---|---|---|
| Auth check | `GET /user/profile` | 10 req/s |
| LTP (REST fallback) | `GET /quote/ltp` | 1000 instruments, **1 req/s** |
| Previous close, in session | `GET /quote/ohlc` → `ohlc.close` | 1000 instruments, 1 req/s |
| Day bars | `GET /quote` → `ohlc`, `volume` | 500 instruments, 1 req/s |
| Previous close, outside session | `GET /instruments/historical/{token}/day` | **one instrument per call**, 3 req/s |
| 1-minute history (`scripts/kite.py intraday`) | `GET /instruments/historical/{token}/minute` | one instrument per call, **at most 60 days per call** (61 → `400`), ~0.8 s for a full 60-day window ✅ 2026-09-27. Bars are stamped at the minute they start. From 3 Aug 2026 the last bar of the day is 15:14 (360 bars a day; 375 before). See [`INTRADAY_HISTORY.md`](../INTRADAY_HISTORY.md) |
| Live feed | `wss://ws.kite.trade?api_key=..&access_token=..` | 3000 instruments/socket, 3 sockets/key |

The quote and historical rate limits are enforced client-side at module level,
because they apply per key and each board runs its own provider. The
after-hours candle lookup for 50 stocks therefore takes about 18 s. It happens
at startup, and again only when the previous-close refresh window comes round.

Every request carries `X-Kite-Version: 3` and
`Authorization: token <api_key>:<access_token>`. Errors come back as
`{"status": "error", "error_type": "...", "message": "..."}`. A
`TokenException` (HTTP 403) means the session is gone, and the fix is to log in
again.

## Websocket

The feed subscribes, then sets `quote` mode. Market data arrives in binary
frames; text frames carry order postbacks and broker messages, and are never
prices. A 1-byte frame is a heartbeat. All values are big-endian, and prices
are in paise (÷100).

Frame: `int16` packet count, then for each packet an `int16` length and the
packet bytes.

| Packet | Bytes | Fields used |
|---|---|---|
| LTP | 8 | token, LTP |
| Stock quote | 44 | token, LTP, volume @16, open @28, high @32, low @36, **close @40** |
| Stock full | 184 | as quote (depth ignored) |
| Index quote / full | 28 / 32 | token, LTP, **high @8, low @12, open @16**, close @20 |

Index packets order high/low/open, and stock packets order open/high/low. The
low byte of the token distinguishes them (`9` = indices).

## Why no `kiteconnect` SDK

Zerodha recommends pykiteconnect. For this service, though, its `KiteTicker`
runs on Twisted, and a Twisted reactor cannot be restarted within a process,
while `LiveMarketDataService` routinely closes and reopens feeds on silence or
failover. The REST API is simple and the packet format is fully documented. So
Kite follows Dhan and INDmoney: `requests` + `websockets`, no new dependency.
